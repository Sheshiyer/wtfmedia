# Beta 0.3 lineage and surface-authority audit

**Recorded:** 2026-09-11 20:37 IST
**Status:** read-only source/runtime reconciliation; no UI fix, deployment, data
copy, queue action, DNS change, Clerk change, tag change, push, or production
mutation is authorized by this audit.

## Finding

There is no single source object called "the latest Beta 0.3." The current
candidate is layered from a release tag, a merged Member Beta branch, an open
Beta integration branch, Pavun57's open RAG branch, and local staging closure.
The deployed staging source contains the intended layers, but one role
conditional selects the older operator chat presentation for editors, admins,
and super-admins. That is why a super-admin does not see the already-corrected
Member/Alpha-derived Beta chat even though that implementation is present in
the same build.

## Where the presentation diverges

The corrected Member chat is not missing. `origin/beta_0.1` contains the
Member/Alpha convergence commits, including `0df461f` (Alpha chat frame),
`6811564` (separate archive/delete UI), `47e1464` (paged history/deletion
receipts), and `6082c6d` (Member chat on the shared Alpha frame).

The divergence is introduced later by `cab6773`:

```text
/beta/chat
  member principal   -> MemberChatWorkspace
  operator principal -> legacy operator ChatWorkspace

/beta/chat/:id
  member mcnv_*      -> MemberChatWorkspace
  operator cnv_*     -> legacy operator ChatWorkspace
```

That conditional is implemented by `web/app/beta/chat/page.tsx` and
`web/components/domain/beta/BetaConversationRoute.tsx`. The super-admin IAB
session therefore exercises the older operator presentation even though the
same deployed bundle contains the bounded Member rail, Alpha-derived thread,
archive/delete, and no-bottom-dock work. This is a mapping regression, not a
need to recreate those components.

## Live staging interpretation

The canonical staging host is serving `abb5413`. A real super-admin Clerk/D1
session resolves, reaches `/beta/workspace`, opens `/beta/chat`, and persists
and reopens `cnv_*` conversations. Two saved UUID conversations in the live
rail prove that the operator history transport and D1 persistence path are
wired.

The answer fallback has a different cause: the isolated staging evidence
plane currently reports zero catalogue R2 objects, zero KV catalogue keys, and
zero Vectorize records. The request reaches the chat path, is persisted, and
then truthfully returns no grounded answer because there is no staging corpus.
No production corpus was copied and no ingest was enqueued during this audit.

## Release impact and next implementation boundary

- Hold Beta production promotion. The deployed staging candidate is useful for
  auth/RBAC/runtime review but is not the correctly mapped final presentation.
- Do not fix the visible UI under this audit. The observed bottom dock,
  unclamped operator session cards, exposed internal Settings entries,
  per-navigation admission screen, and unavailable operator roster remain
  acceptance findings against `abb5413`.
- The next code slice must adapt the existing signed-in chat presentation to
  both member and operator server contracts. It must not start another chat UI
  implementation or replace Pavun57's inference symbols.
- Grounded staging inference requires a separately approved, provenance-safe
  staging corpus operation. Production data must not be copied down merely to
  make the demo pass.
